# Daymark automation events

Daymark sends three events to the automations an organization's admin built in **Automations**
(powered by viaSocket). This page is the contract: when each event fires, exactly which fields it
carries, and where every value comes from. The same field list is shown inside the app.

**Source** column: *Daymark* = supplied automatically by Daymark's backend. Nothing in these events is
typed by a user per run, generated by AI, or returned by an external app. What the *automation* then does
with the values (which channel, what wording) is chosen once, by the admin, in the builder.

## Delivery guarantees — read this before building an automation

* **At-least-once.** Daymark retries a delivery when it can't tell whether viaSocket received it, so the **same
  event can arrive more than once** (and a duplicate request to Slack/email is then possible).
  Every payload carries a stable **`eventId`** — the same value on every retry and resend. If a duplicate message
  matters, have the automation remember `eventId` and skip ones it has seen.
* **Stable IDs.** `eventId` = `evt_` + a hash of (organization, event key), e.g. `update.submitted:<updateId>`.
  The same logical event always has the same ID.
* **Retries.** Network errors, timeouts, `408/425/429` and `5xx` are retried up to 5 attempts in total, waiting at
  least 5 min, 30 min, 2 h, then 6 h between attempts (retries run on the cron sweep, so real timing is the next
  cron run after each delay). `attempt` in the payload says which attempt this is.
* **Not retried:** other `4xx`, redirects, and a paused/deleted automation (the delivery is marked *Skipped*).
* **"Accepted" ≠ "worked".** A 2xx means viaSocket received the event. A failing step inside the automation (for
  example Slack rejecting a message) still answers 2xx — check the automation's run history in viaSocket.
* **History.** Every attempt (time, duration, HTTP status, result) is kept and shown under *Delivery history*.
  URLs, payloads and response bodies are never stored in the history.
* **Retention.** Event payloads are deleted after 30 days; the delivery history after 180.
* **Isolation from core.** Events are created only after the core action has committed, in a try/catch; any
  failure is logged and swallowed. Daymark never waits for viaSocket.

## Envelope (every event)

| Field | Source | Notes |
|---|---|---|
| `schemaVersion` | Daymark | `1` |
| `eventId` | Daymark | Stable; dedupe on this |
| `eventType` | Daymark | `update.submitted` · `update.blocker_reported` · `update.missing` |
| `occurredAt` | Daymark | ISO-8601 UTC |
| `test` | Daymark | `true` for "Send test event" (synthetic data, never real people) |
| `organization.name` | Daymark | |
| `attempt` | Daymark | `1…5`, added at send time |

## `update.submitted` — Daily Update Submitted

Fires **once**, when an employee first submits an update (not for drafts, not for later edits).
Event key: `update.submitted:<updateId>`.

| Field | Source | Why it's included |
|---|---|---|
| `employee.name` | Daymark | who |
| `employee.team` | Daymark | where (`null` if none) |
| `update.date` | Daymark | the day the update is for |
| `update.isLate` | Daymark | submitted after the cut-off |
| `update.hasBlockers` | Daymark | headline fact |
| `update.url` | Daymark | link into Daymark (sign-in and permission still required) |
| `manager.name`, `manager.email` | Daymark | the natural recipient: the employee's manager, else their team's manager; `null` if none or deactivated |

Never included: the update's text, links, completed/pending work, AI output, the employee's email.

## `update.blocker_reported` — Employee Reports a Blocker

Fires **once per update**, the first time it contains a real blocker — at submission, or when a later edit
adds one. "None", "N/A", "no blockers" etc. don't count. Event key: `update.blocker_reported:<updateId>`.

| Field | Source | Why |
|---|---|---|
| `employee.name`, `employee.team` | Daymark | who |
| `update.date`, `update.url` | Daymark | context + link |
| `manager.name`, `manager.email` | Daymark | recipient |
| `blocker.count` | Daymark | how many real blockers |
| `blocker.text` *(optional)* | Daymark | **Only if an admin turned on "Include blocker text"** (off by default): the first blocker, truncated to 280 characters |

## `update.missing` — Daily Update Missing

Fires **at most once per person per day**, from the cron job. Conditions: the organization's cut-off time (in its
own timezone) has passed on a working day; the person is active and joined before that cut-off; they have no
*submitted* update for the day (a draft doesn't count); and the organization has an active automation linked to
this event. Event key: `update.missing:<membershipId>:<YYYY-MM-DD>`.

| Field | Source | Why |
|---|---|---|
| `employee.name`, `employee.email`, `employee.team` | Daymark | recipient of the reminder |
| `reminder.date` | Daymark | the day that's missing |
| `reminder.submitUrl` | Daymark | one click to the update form for that day |
| `reminder.cutoffTime`, `reminder.timezone` | Daymark | wording ("by 18:00 IST") |

No manager data and no work content.

```json
}
```
